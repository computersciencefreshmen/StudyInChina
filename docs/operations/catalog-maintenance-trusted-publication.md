# Cloud candidate publication credentials

The cloud publisher keeps candidate evidence, canonical application and verified public publication separate. A new changed candidate is committed on `codex/cloud-catalog-<run>-<attempt>`, checked by the existing full CI, and pushed to protected `main` only as the exact tested SHA. The base must still equal the original parent before the commit and after CI. Main is never force-pushed or rebased, and repository protection remains authoritative.

GitHub's required-check rules distinguish event origins: successful manually dispatched CI does not substitute for the trusted push check needed here. The CI push filter therefore includes `main` and managed `codex/cloud-catalog-*` branches. The publisher waits for a completed, successful `push` run matching both the candidate SHA and branch, and relies on the resulting main push to trigger its own CI. See [GitHub's required-check guidance](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) and [GITHUB_TOKEN event limitations](https://docs.github.com/en/actions/concepts/security/github_token).

Unattended new publication requires the separately configured repository secret `CATALOG_PUBLISH_GITHUB_TOKEN`. Use a dedicated credential restricted to this repository with **Contents: read/write** and **Actions: read**; no pull-request creation or branch-protection bypass permission is needed. This change does not create, copy or configure a credential. Tokens and local authentication must not enter the repository, artifacts or chat.

Checkout uses that dedicated secret when available and otherwise uses `github.token` so existing recovery can continue. Only the changed-candidate publication step requires the dedicated secret. If absent, it emits an actionable error before creating a commit, pushing a branch or waiting for CI; the immutable Worker export remains held for a later authorized run. It does not acknowledge application or discard the candidate.

Already applied batches, lost-acknowledgement recovery, unchanged/held-candidate acknowledgements and stable-publication readback retain their existing guards and do not require the new secret. The existing recovery-only missing-main-CI dispatch uses `github.token`; new dedicated-token pushes do not add redundant branch or main dispatches. Adding the secret enables this path but does not override failed CI, a changed base, access restrictions or normal protected-branch rules.
