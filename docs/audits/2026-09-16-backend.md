# Backend trust and validity audit — 2026-09-16

## Scope and architecture

The public site reads either a generated JSON compatibility bundle or a Catalog D1 release. The ingestion/publisher pipeline owns evidence, candidate validation and release preparation; public repositories own publication filtering and response projections; Next.js and the Catalog Worker own HTTP delivery. An immutable release does **not** imply that its application status stays current: the same deadline must change state as the China calendar advances.

This review inspected local schemas, publication/freshness helpers, JSON/D1 repositories, API field projection, HTTP handlers, D1 application views, ingestion fetch restrictions and feedback origin/rate-limit/Turnstile handling. Next.js changes were checked against the installed Route Handlers and CDN Caching guides before editing. Source-page re-verification and dependency upgrades are tracked by the parallel data and project audits.

## Findings and implemented repairs

| Priority | Finding | Repair and practical effect |
| --- | --- | --- |
| P1 | D1 treated a future deadline with no opening date as `open`, whereas JSON correctly said `dates-published`. A rolling window with a future opening date was also immediately marked `rolling`. | Added migration `0011_application_state_calendar.sql`; aligned Worker state selection and SQL filters with JSON: closed → upcoming → rolling → open only with an opening date → dates-published → not-announced. Applicants are no longer told that an unproven application window is open. |
| P1 | `CONTENT_PREVIEW=true` was rejected only when `VERCEL_ENV=production`; a self-hosted `NODE_ENV=production` process could therefore return draft data. | A shared preview gate now permits explicit Vercel Preview, local development and tests only. Both synchronous and repository loaders use it. |
| P2 | The Catalog Worker reused one release/date ETag for all resources and filters, and evaluated it before validating the requested path or query. An unrelated validator could return `304` for an invalid or missing resource. | Public responses hash their actual JSON representation after successful routing/query evaluation. Correct conditional GET, weak validators, HEAD, 400 and 404 behavior is covered. Internal authenticated artifact delivery remains separate. |
| P2 | Public Next API responses allowed a five-minute shared-cache lifetime plus one hour of stale delivery, including across China midnight when reviews or deadlines expire. | Next and Worker share a cache policy whose fresh and stale windows end before China midnight; the final partial second is `no-store`. Default stale delivery is capped at five minutes. Error/not-found responses are not cached. |
| P2 | Legacy SQL application filters used UTC `date('now')`, unlike China-calendar public views, and an `OR` fallback could match a legacy interpretation even when a normalized window existed. | Fallback dates now use UTC+8. When a normalized application window exists, the normalized state is authoritative for filter matching. |
| P2 | D1 operational release metadata could retain yesterday's `evaluatedForDate` for the remainder of its process cache lifetime. | The metadata cache is additionally keyed to the China calendar date. Both remote fetch paths explicitly use `cache: 'no-store'`, leaving the bounded repository cache in control. |
| P2 | SQL behavior tests required real catalogue items with unexpired confirmed tuition and scholarship funding/deadlines. They failed merely because admissions expired. | Tests add one explicitly synthetic current program/cycle and two scholarships to their in-memory input bundle. The original filtering/sorting/cursor assertions remain; production files receive no fabricated facts. |

D1 already rejects a rolling window with a non-null closing date via a table CHECK constraint. The rolling regression for the real normalized database therefore uses its allowed case: a rolling window whose opening date is still in the future. The pure helper also handles contradictory legacy input defensively.

## Runtime freshness review

- JSON repository singletons cache **raw** bundle parsing, not dated public projections. Lists and comparisons resolve the calendar again on each request.
- `getCatalogData()` passes today's China date to the publication filter. React request memoization does not turn that date into a deployment-time constant.
- D1's 60-second compatibility snapshot cache retains immutable raw data; the page loader still applies current-day publication rules afterward.
- Detail pages had their own static-rendering lifetime outside these repositories. The project integration audit owns the change to request-time rendering for pages that expose dated facts, including metadata paths.
- New migration `0011` must be applied to Catalog D1 before considering the D1 path ready. Local migration validation and Worker dry runs do not prove that a remote database has applied it.

## Remaining work and limits

1. **Production proof:** no remote migration, queue processing, publication cutover, rollback or backup/restore readiness is inferred from these local checks. Retain the existing D1 shadow and cutover gates.
2. **Data depth:** a valid identity or reachable official URL does not verify current tuition, eligibility, funding, teaching language or an application deadline. Field-level official evidence and review dates remain required; the parallel data audit owns re-check results.
3. **Legacy provenance:** JSON carries record-level evidence, whereas D1 supports field-level evidence. A legacy record citing several URLs is not proof that every displayed field is independently grounded. Continue source-manifest and field-evidence migration before claiming complete coverage.
4. **Performance:** normalized application-state filters still compose several large public views and correlated fallback clauses. The full-catalogue state regression required about 32 seconds for four requests on the local test setup while other jobs were active; this is a diagnostic observation, not a production latency benchmark. Run the dedicated catalogue benchmark and inspect D1 query plans before cutover. Semantic regressions use a separate fully migrated synthetic database to keep correctness tests focused.
5. **Review completeness:** this is a source-code and local-test audit, not a penetration test or a certification that every branch, external service and live university source has been exercised.

## Design trade-offs

The response ETag is now a real representation hash. This retains bandwidth savings from `304`, but the Worker must evaluate the query before it can know that the response is unchanged. That cost is deliberate: a catalogue-wide hash cannot safely validate arbitrary filtered content. A future query cache can key on release, China date, normalized route and query after validation, with measured latency and explicit invalidation.

Request-time evaluation and shorter cache windows trade some cache efficiency for correct deadlines. Raw immutable bundles remain reusable, so checking the date does not require reparsing every source file or repeating ingestion.
